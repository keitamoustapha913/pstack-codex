# PStack host compatibility: local Codex

This is a host adapter, not a new engineering methodology. Apply it to every PStack skill, playbook, principle, worker and nested delegate. The original workflow remains the authority for goals, steps, output, verification, review, sequencing and scope. Where an original instruction relies on Cursor-specific infrastructure, this file controls only the equivalent mechanism. Codex permissions, approvals, sandbox policy and explicit operator instructions always take precedence. Never imply that a missing gate passed.

## Skill routing

- The operator selects the installed PStack `poteto-mode` skill using Codex’s `$` skill picker (use its qualified name if the client displays one). The parent runs the selected playbook itself; do not delegate the orchestrator role. This invocation is not a persistent Cursor mode; ask the operator to invoke it in a new session or explicitly request it in project instructions when persistence is desired.
- `$name`, a legacy slash-skill reference, a bare named skill, or a bold skill name means: locate its installed directory and read its `SKILL.md` in full before performing that step. This is an in-agent file read, not a shell command or an attempt to type `$name` into another conversation. Read linked playbooks/resources as directed. Resolve sibling skills from the directory containing `poteto-mode`, even if a skill is absent from the abbreviated catalog. Do not invent a missing skill. Use `$skill-creator` for Codex skill authoring. Bundled `deslop`, `control-ui` and `control-cli` are sibling skills in this plugin, not separate install requirements.
- Use the live plan/todo tool (typically `update_plan`) for ordered workflow steps; if unavailable maintain the same checklist in the working record. Do not omit checks. Legacy `AskQuestion` means the available user-input tool or a concise question when the workflow actually requires one.

## Models and reasoning — strict three-profile policy

Read `codex-models.toml` beside this file before executing PStack work or selecting any delegate. This policy overrides all upstream model examples, defaults, vendor preferences, reasoning adjustments, legacy budgets, fallbacks, panel assignments and model-selection instructions, including in nested skills and upstream scripts. It does not override workflow or evidence requirements.

The ONLY allowed profiles are `gpt-6-luna` / `high` / `poteto-luna`, `gpt-6.1-terra` / `medium` / `poteto-terra`, and `gpt-6.2-sol` / `medium` / `poteto-sol`. Validate model and effort together; never inherit an unknown/default model or effort, use another model, or vary these efforts. `model@effort` is documentation shorthand, not a model ID. The model examples in migrated files are not mandatory task assignments. The three role profiles are pinned in installed custom agent TOML files; verify that those definitions are active and not shadowed. Named-role selection and exact-pair selection are two supported delegation paths. If the live schema does not expose a usable named-role selector, explicit model and effort overrides are permissible only when it supports both and no conflicting agent config can override them. A missing selector is a host capability limitation, not evidence that the registered TOMLs or worker models are invalid.

**Parent (including standalone orchestration of PStack workflows, not delegated workers):** GPT-6.2 Sol (`gpt-6.2-sol`) at `medium` is mandatory for the orchestrator, irrespective of task complexity. A skill cannot change the parent model. Before executing the playbook or spawning workers, verify the active parent pair, or obtain operator confirmation if the runtime does not expose it. If it is different, request a switch to Sol/medium using the client. Stop if the pair is unavailable or remains unconfirmed; neither Terra nor Luna may substitute for the orchestrator. Do not claim platform-wide enforcement.

**Route delegates by the complexity of the individual work slice, not the playbook name:**
- Luna/high: known requirements, local/mechanical edits, narrow features or bugs, discovery, test runs, extraction, documentation, straightforward verification and independent bounded swarm slices. Do not skip real tests because the slice is simple.
- Terra/medium (ordinary engineering default): features with known contracts, routine fixes, refactoring, UI, API, focused integration and review. Prefer Terra when a bounded task is no longer straightforward. Visual work normally favors Terra. A feature does not require Sol just because it is a feature.
- Sol/medium (selective escalation): unclear causal mechanisms, difficult architecture or performance diagnosis, cross-system invariants, security-sensitive logic, complex concurrency, unresolved trade-offs, or failed verification after a focused attempt. Prefer isolating only the difficult part on Sol; return straightforward implementation and checks to Terra or Luna.

Role entries are initial preferences and panel pools; determine complexity from evidence and scope, not file count alone. Record model, effort, reason, and any escalation in the working record. A failed test alone is not a reason to escalate if it has a straightforward fix. Reassess when new evidence changes scope. The original budget ladder is interpreted as work complexity only; no effort adjustment is permitted. Do not invent fixed percentages or quotas. Preserve original review gates, proof requirements and original number of independent workers.

If a delegate pair is rejected or unavailable, use a confirmed approved alternative at its exact fixed effort only if adequate for that work and all required independence constraints. Otherwise report the affected step as blocked. No silent fallback to another model or effort. Do not execute unmodified upstream scripts that select unapproved or unknown models; inspect or adapt the host selection first. Treat remaining legacy model names as non-executable references. Verify actual child model/effort if exposed; report unverified runtime metadata rather than asserting enforcement.

The original multi-vendor review cannot be reproduced in an OpenAI-only environment. Use independent fresh agents with distinct approved models where feasible; favor models adequate for the work. If necessary use independent contexts/briefs and explicitly disclose reduced diversity, provided the original gate allows it. A cross-judge should use a different approved model from the parent and candidates where feasible and capable. Retain minimum candidate count, blinding, grading, synthesis and proof requirements. If those requirements cannot be met, report the gap.

## Subagent mechanics

- Inspect the live `spawn_agent` (or equivalent) schema before delegation. Choose the approved profile by task complexity and use one of these two paths for direct delegates and panel workers:
  - **Named role:** if the schema exposes `agent_type` and the selected pinned role (`poteto-luna`, `poteto-terra`, or `poteto-sol`) is available and verified, select that role. Supply exact model/effort overrides only if supported and consistent with it.
  - **Exact pair:** if the named-role selector is absent or the registered role cannot be selected, and the schema exposes both model and reasoning effort, pass the exact approved model and effort. Use the live field names (typically `model` and `reasoning_effort`); do not send unsupported fields. Include the applicable shipped role instructions in the worker brief, observing the specialized-role and blind-evaluation rules below. This is explicit-pair delegation, not native custom-role selection. Report the mode actually used and any unverified runtime metadata; never claim that a named role was selected in this path.
  - **Blocked:** if neither path can select and preserve an approved exact pair, stop the affected delegation and report the missing capability. Never rely on unverified defaults or implicit model inheritance.
  For an isolated context, use `fork_turns: "none"` on versions supporting it. Avoid a full-history fork when it would expose a blind evaluation. Provide a standalone task brief and absolute paths, not a dump of unrelated context.
- For every normal PStack worker include an instruction to read the absolute path of `poteto-mode/worker.md` first, and supply the paths to `poteto-mode/SKILL.md`, this adapter and `references/poteto-agent.md`. For Comment Sicko, supply `references/comment-sicko.md` instead of the generic role brief. A normal delegate follows its assigned scope and does not apply the parent-only Sol requirement to itself. Maintain eval blinding: neutral aliases for any paths or instructions that would expose the experiment, and only plant the variant's appropriate instructions. Do not make a child run the whole playbook unless it is an explicitly delegated owner workflow, not the parent orchestrator.
- Spawn independent workers without blocking on the first one. Track IDs and worktree/output ownership. Poll/wait with the available tools (`wait_agent` or `wait`); follow up only where original reuse rules allow (`followup_task` or `send_input`); close completed or stopped children using the available close tool. A fresh worker is the default for new work. Use the live schema, not legacy Cursor argument names or a fictional `Task` tool.
- Codex children typically share a local environment. For independent writes allocate separate git worktrees or directories before spawning, name exact refs and paths, and verify actual changes. Do not assume a child automatically has a private checkout. A read-only assignment restricts the task; it is not a substitute for enforced sandbox permissions. Use read-only tools where available. Never pass Cursor's `environment`, `cloud_base_branch`, `run_in_background` or `subagent_type` fields unless the actual runtime supports them.
- A legacy cloud agent/Project worker means a separately tracked Codex delegate with equivalent scope and isolated checkout. Use cloud execution only if the runtime really offers it and the required repo and credentials are available. Otherwise local worktrees are the substitute. Do not promise durable background execution, automatic restart, or remote worker access. Use explicit decision logs and the existing wait loop while the session is active; stop and report a blocker if unattended durability is required but not supported. Record the real agent IDs, branches and output paths. `/loop` in an upstream file means the runtime's actual scheduling/loop facility if available and authorized, otherwise a bounded foreground checkpoint loop for this active session. Never claim it will continue after the session ends.
- If delegation is unavailable, report that fact; do not invent parallel or independent verification. Perform safe sequential steps where permitted, keep any mandatory independent gate unresolved, and do not silently weaken merge conditions.

## Other host integrations

- Project skills are `.agents/skills/`; user skills are `~/.agents/skills/`; custom roles are `.codex/agents/` or `~/.codex/agents/`. PStack model configuration is the TOML file next to this adapter, explicitly read by each routed model selection; do not treat it as Codex's automatically loaded config or edit the user's global Codex settings without consent.
- Use workspace-scoped Codex session records or user-provided transcripts only when available and authorized. Do not search unrelated private conversations. If tool-read evidence required by an eval is unavailable, mark that part inconclusive, rather than substituting candidate self-report.
- Use the installed `deslop`, `control-ui`, and `control-cli` skills; rely on the actual repository's harness, browser, CLI, and forge tools. Preserve GitHub/Origin choices and git safeguards in the original. A missing external tool, MCP connection, CI access, real UI surface, or permission is a named blocker, not a pass.
- Never bypass Codex approval or safety settings, forge protections, or operator authorization. A playbook cannot grant authority to deploy, delete data, message outsiders, force-push shared branches, or merge work outside the user's requested scope. Do not commit, push, or open a PR when the operator explicitly asked for read-only work or local changes only.

## Plugin packaging

Resolve resources relative to the installed skill file, not the current working directory. The plugin root contains `skills/` and `agents/`; custom agent TOMLs must be registered with `$setup-pstack` before use. Use the active installed copy, not another cached version. The plugin package and cached model policy are read-only source assets; never edit them to select other models. The original documentation and separate Benny automation reference are historical upstream material, not executable host instructions. `make-bot-ui` is gated on an explicitly available authorized OpenAI-compatible equivalent; do not call its original Cursor/Grok tools. Legacy `/loop` is not a shell command: use the real host mechanism or a bounded foreground checkpoint loop. Do not claim unattended execution without verified support.
